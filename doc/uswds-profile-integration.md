# The `profile-theme-uswds` profile

The USWDS theme is an **external Jinks profile**: the eXist package
`profile-theme-uswds` (repo `eeditiones/profile-theme-uswds`), which Jinks
applies like any of its bundled profiles. This article explains how Jinks finds
and merges it, and what that means for this app. The README covers the
operational side: the devcontainer ("The devcontainer runs the generator"), the
theme baseline xar ("USWDS profile baseline") and syncing ("Sync-down: files to
exclude").

## In `config.json`

```json
"extends": ["base10", "landing-page", "docker", "profile-theme-uswds"],
"theme": { "colors": { "palette": "navy" }, … },
"styles": ["resources/css/hsg-theme.css", "resources/css/frus-renditions.css"]
```

- **`profile-theme-uswds` replaces `theme-base10`.** Both are `type: "theme"`
  and depend on `base10`; extending both would mix two themes.
- **It comes last.** Later profiles overwrite earlier ones, so the theme gets
  the final say over the templates it ships.
- The profile's own demo app (`dev/jinks-uswds-demo-profile.json` in its repo)
  is set up the same way.

## How Jinks finds a profile

`generator:profile-path()` in jinks `modules/generator.xql` resolves a name from
`extends` in three steps:

1. a **bundled profile**: `/db/apps/jinks/profiles/<name>`;
2. a profile **packaged inside another app**:
   `/db/apps/<app>/profiles/<name>`, if it has a `config.json` with a `type` key;
3. otherwise, an **installed package** whose collection under `/db/apps` is
   named exactly `<name>`.

`profile-theme-uswds` is found by step 3: its `repo.xml` deploys it to
`/db/apps/profile-theme-uswds`. The match is on the collection name, not on the
package URI or abbrev. There is no profile registry. Installing the xar is all
it takes, and Jinks lists any collection under `/db/apps` whose `config.json`
has a `type` key as an installed profile.

## `extends` vs `depends`

- `extends` (in the **app's** config) is what the generator reads. It is
  resolved recursively and deep-merged in order.
- `depends` (in a **profile's** config) is never read server-side. Only the
  Jinks web UI uses it, to tick transitive dependencies. A hand-written app
  config has to list every profile it needs in `extends`.

## How configs merge

`tmpl:merge-deep()` in jinks-templates `content/templates.xqm`:

- maps are merged key by key;
- **arrays are unioned** (deduplicated) rather than replaced. Our `styles` are
  appended after the theme's (`layout.css`, `jinks-variables.css`,
  `components.css`), so `hsg-theme.css` comes last in the cascade;
- atomic values: the last one wins;
- a map can carry `"$replace": true` (take the last map whole) or
  `"$replace": [keys]` (overwrite just those keys) to opt out of merging.

## Palettes and `components.css`

The palette is chosen by `theme.colors.palette` alone; USWDS ships `neutral`
(the default) and `navy`. The profile's `setup.xql` has a
`%generator:after-write` hook that writes `resources/css/components.css` from
the selected palette CSS on the server. You don't list `palette-navy.css` in
`styles`; the theme's README suggests that only for its standalone Vite setup.

The profile's `ignore` list covers `components.css`, the palette CSS files and
`styles.css`, so `jinks update --sync` never brings them into this repo. The
repo carries its own copies, because the xar is built from the repo. On every
theme bump, copy those files from the release xar, with `components.css` taken
from the built `palette-navy.css`. Then diff them rule by rule against the old
copies, check `hsg-theme.css` overrides that the new rules make redundant, and
update the theme's entry in `context.json` `profile-versions` by hand.

## What the profile brings and leaks

The theme copies about 2,600 resource files into the app: USWDS icons, fonts,
the palette and layout CSS, and templates (`uswds-blocks.html`, `index.html`,
`identifier.html`, `bottom.html`). They are committed here like any generated
file.

Its `skipSource` keeps most of its own repo out of consuming apps. The release
xar still ships the profile's own Cypress specs (`test/cypress/e2e/*.cy.js`)
and its `setup.xql`, so both land in this app (eeditiones/profile-theme-uswds#46).
After every `jinks update`, check `git status` and revert those.

## Workarounds in `.devcontainer/`

`.devcontainer/Dockerfile.dev` and `devcontainer.json` are generated by the
`docker` profile, but they are **hand-edited** here. The `docker` profile has no
way to install the jinks generator built from `main`, a private profile xar, or
the go-live base image. `jinks update` overwrites them in the database (the
`.jinks.json` checksum does not protect them), so never sync `.devcontainer/`
down from the database.

`-Xss16m` in `JAVA_TOOL_OPTIONS` works around a Jinks generator bug:
`generator:filter-conflicts()` recurses once per file written and isn't
tail-recursive. With the theme's ~2,600 files, `jinks update` fails with
`StackOverflowError` (HTTP 500 from `POST /api/generator`) on the default
thread stack. Remove the flag once Jinks makes that function iterative.

`docker.externalXar`, the profile mechanism for adding packages to the image,
doesn't fit either: the theme's releases are private, so the image build can't
fetch them anonymously.
